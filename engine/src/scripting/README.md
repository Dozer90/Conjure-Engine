# scripting

C# scripting on the .NET 8 runtime: one CLR per process started through hostfxr, a versioned native API
table the managed SDK calls through function pointers, `script_component` entries that own managed
instances by slot, the six exclusive script systems, hot reload through a collectible load context with
field preservation, `[EcsComponent]` mirrors registered into the component registry, DOD `Span<T>` query
scopes, and `dotnet build` driven from the engine. Static library `conjure::scripting`, namespace
`conjure::scripting`, public dependencies `conjure::core`, `conjure::ecs` and `conjure::assets` (never
`conjure::scene`, R29); the .NET hosting headers are a private dependency. Binding design:
`docs/design/03_scripting.md`; ARCHITECTURE 6; `docs/design/09_cross_area_resolutions.md` R4-R6, R26-R29,
R36, R39, R54, R61, R64.

Private files: `hostfxr_api.h` (the only file that includes `nethost.h`, `hostfxr.h` and
`coreclr_delegates.h`; `host_string`, `host_status`), `hostfxr_runtime.{h,cpp}` (the process-wide CLR:
locate hostfxr, initialise for the runtime config or the self-contained command line, load
`Conjure.Bootstrap` and fetch its `Initialize` export), `native_api_core.cpp` (the 20 core entries:
log, class registration, faults, entities, components, queries), `native_api.cpp`, `script_runtime.cpp`,
`script_component.cpp`, `script_fields.cpp`, `script_class_registry.cpp`, `script_host.cpp`,
`dotnet_script_host.cpp`, `null_script_host.cpp`, `script_system.cpp`, `hot_reload.cpp`,
`managed_build.cpp`, `scripting_error.cpp`, `log_category.cpp`.

The managed side lives in `managed/`: `Conjure.Managed` (the SDK: `ScriptBehaviour`, `Entity`,
`Transform`, `Input`, `Time`, `Log`, `Physics`, `Audio`, `Prefab`, `Scene`, `Dod.ComponentQuery<T>`,
`[EcsComponent]`, the interop layer and the guard), `Conjure.Bootstrap` (the assembly hostfxr loads;
owns the runtime config), `Conjure.TestScripts` (the scripts the `[dotnet]` tests drive, built as
variants V1/V2/V3 for the reload tests) and `Conjure.Templates/Game` (the project a new game starts
from). `cmake/ConjureManaged.cmake` builds them with `dotnet build` behind stamp files; a project's stamp
depends on the stamps of its managed `DEPENDS`, so an SDK change rebuilds the test scripts.

Mirror and `[EcsComponent]` layouts (`LayoutHash.cs`) are the managed layouts `sizeof(T)` and `Span<T>`
use: fields at their natural alignment in declaration order (or their `[FieldOffset]`), checked against
`Unsafe.SizeOf<T>`. `Marshal.OffsetOf`/`SizeOf` are never consulted, because they widen `bool` to 4 bytes
and would disagree with the memory native reads. `ComponentType<T>.Id` is cached per handshake generation
(`NativeBridge.Generation`), so a new runtime with other component ids re-resolves; a 0 is never cached.
`ScriptRuntime.Shutdown` forgets the native table (`NativeBridge.Reset`): the host may free it right after.

## Using it

```cpp
component_registry registry = {};
CONJURE_TRY_ASSIGN(const component_id scriptComponent, register_script_component(registry));
world world(registry);

script_runtime runtime(create_script_host(script_backend::DOTNET));
script_runtime_config config = {};
config.host.managedDirectory = executable_directory() / "managed";
CONJURE_TRY(runtime.initialize(config));
runtime.attach_registry(&registry);
runtime.attach_world(&world);
CONJURE_TRY(runtime.load_game_assembly(project / "bin" / "Game.dll"));
runtime.set_mode(script_mode::PLAY);

scheduler scheduler(world, &jobs);
hot_reload_controller reload(runtime, project / "bin" / "Game.dll");
CONJURE_TRY(register_script_systems(scheduler, runtime, &reload));

const script_entry_id id = runtime.add_script(player, script_name_hash("Game.Player"), fields.root());
if (!id.is_valid()) {
    // dead entity, detached world or a full set: logged by the runtime
}
```

`add_script` queues the managed instance; `flush_pending()` (run by the frame_begin system and by every
`run_phase`) creates it, so the entry has a slot from the next phase on. Fields travel as the blob of
`script_fields.h` both ways: `set_field` applies one, `collect_entry_fields` refreshes the JSON the entry
keeps, which is also what `serialize_entity_scripts` writes.

## Threading

Everything is main-thread only: the CLR is started and every managed call is made from the thread
`core::jobs::is_main_thread()` names, and every native entry but `log_write` asserts on other threads and
fails softly (0 / `-NOT_INITIALIZED`; the SDK throws `InvalidOperationException` before reaching native, so
only a raw function pointer captured by a `Task` gets that far). `managed_build_runner` is the one
exception: the build process runs on a job and its report is posted with
`core::jobs::post_to_main_thread`, so the caller drains that queue. The frame block is written by native
before each phase and read by managed during it.

## Destruction order

A `script_runtime` must be detached (or destroyed) before the `world` it is attached to: the
`script_component` hooks resolve the runtime through `script_runtime::active()` while the world frees
its entities, and the runtime's observers are unregistered by `attach_world(nullptr)` / the destructor.
Declare the runtime after the world (the test fixtures do) and `shutdown()` it before the world dies.

## The component registration

`register_script_component` registers the component through `component_registry::register_described` with
`component_type_desc {ops = script_component_ops(), serializer = script_component_serializer(), reflection =
nullptr}`: the copy hook deep-copies the set, destruct frees it, `writeJson` / `readJson` carry the
`{"scripts":[...]}` form and `remapEntities` rewrites `ENTITY` fields through the class schema (the ECS
consults it for types without reflection). Every ECS path (`component_to_json`, `write_archive_json` /
`read_archive_json`, archives, scene files, prefabs, snapshots) therefore carries scripts without the scene
module knowing scripting exists (R29); `tests/scripting/test_script_component.cpp` and
`tests/integration/test_scripting_scene.cpp` assert the round trips. All hooks resolve the runtime through
`script_runtime::active()` and do nothing when no runtime is alive.

## Re-entrancy and sessions

Every managed call may run script code that calls back in: `OnCreate` may destroy its own entity,
`OnDestroy` may spawn scripted entities (the store reallocates), either may open a query scope. The
runtime therefore never holds a `script_set *` or `script_entry *` across a managed call, destroys the
instance of a request whose entry vanished during `create_instances` in the next flush iteration, and
force-closes scopes left open by a managed call. `OnCreate`/`OnDestroy` run inside the phase whose flush
created them (query scopes allowed); the flushes of `frame_begin`, `frame_end` and `set_mode` run no
phase, so `ComponentQuery.Begin` there is `NOT_IN_PHASE`. Collision callbacks run as `FIXED_UPDATE`.

`set_mode(EDIT)` / `destroy_all` end a play session: `STARTED` and `FAULTED` are cleared so the next
`PLAY` runs `OnStart` again (the started flag is for hot reload only, D8); a reload clears `FAULTED` and
first drains the pending destroys so no detached slot keeps the retired load context alive.
`attach_world(other)` destroys the live instances of the old world without `OnDestroy` (WARN when any
exist) and adopts the sets the new world's entities already carry; `set_mode(PLAY)` and reload create
instances for the attached world's entities only.

## DOD query scopes

`begin_query_scope(typeIds, out)` is the native side of `ComponentQuery.Begin<T...>()` (03_scripting.md 3.9)
and the path `scripting.update_10k_dod` gates at zero allocations per frame (08_testing.md 7.1). Nothing on it
touches the heap once warm:

- The `ecs::query` behind a scope is cached per component set in `mQueryCache`, a `core::flat_map` keyed by
  the sorted, deduplicated, `component_id::INVALID`-padded ids (`std::array<u16, QUERY_MAX_COMPONENTS>`), so
  `{a, b}`, `{b, a}` and `{a, a, b}` share one query while the chunk views keep the columns in the order of
  the request (a repeated id names the same column twice). A cached query refreshes incrementally (new
  archetypes only) and belongs to the attached world: `attach_world` drops the cache; `stats().cachedQueries`
  and `cached_query_count()` report its size.
- A `query_scope_state` keeps its chunk views in a `core::small_vector<conjure_chunk_view,
  QUERY_SCOPE_INLINE_CHUNKS>` (16 inline: 10,000 rows of a 12-byte component are 13 chunks of 819 rows) and
  its types in a `core::small_vector<ecs::component_id, QUERY_MAX_COMPONENTS>`. States are heap-owned
  (`std::unique_ptr`) because managed holds `conjure_query_scope::chunks` for the scope's lifetime and an inline
  buffer would move with the state; a finished state is not destroyed but moved to `mFreeQueryScopes` (its
  block and any spilled capacity included). `take_scope_state(chunkCount)` reuses them best-fit: the free
  state with the smallest capacity that holds the scope's chunk views, or the largest one when none fits (it
  spills, once per size step). A scope therefore allocates only when no free state has room for it, whatever
  order nested scopes were closed in; with a steady entity count each state spills at most once and the path
  is allocation-free from then on. In Debug and Development a closed state's view array is memset to `0xDD`
  (03_scripting.md 3.9): a `conjure_chunk_view` pointer that escaped its scope reads `0xDD` until a later
  `begin_query_scope` reuses that state.
- `mQueryScopes` and `mFreeQueryScopes` are reserved once in the constructor (`QUERY_SCOPE_RESERVE` = 4, the
  nesting depth scripts realistically reach); `erase` never releases capacity.

`tests/scripting/test_dod_query.cpp` holds the gates: a null-host case opens and closes a scope 100 times
after a warm-up under `CONJURE_CHECK_NO_ALLOCATIONS`, a null-host regression nests a scope over 19 chunks
with a one-chunk scope in both orders, closes the outer one first and requires 0 allocations from the second
frame on, a `[dotnet]` case runs `PositionWriter` for ten frames and requires an allocation count of 0 from
the third frame on.

## nethost on MSVC

The static `libnethost.lib` of the host pack is built against the static release CRT, which the engine's
`/MD` and `/MDd` objects cannot link (LNK2038). On MSVC this module links the `nethost.lib` import
library instead and copies `nethost.dll` next to the executables after each build of `conjure_scripting`;
other platforms link `libnethost.a` through `conjure::thirdparty::nethost`.

## How to test

```
python tools/build.py --build-dir build/<dir> --target conjure_scripting_tests --test -R "scripting|managed"
```

The null-host tests always run; `null_script_host` hooks (`set_create_hook`, `set_destroy_hook`,
`set_phase_hook`, `set_collision_hook`) stand in for script code, so re-entrancy and the query-scope
paths of `native_api_core.cpp` are covered without .NET (`test_native_entries.cpp`). Cases tagged
`[dotnet]` start the real runtime from `bin/managed` (built by `conjure_managed_sdk`) and are skipped
through `precondition::DOTNET_RUNTIME` when no .NET 8+ runtime is installed. The cases that spawn
`dotnet` themselves (the self-contained publish, the test-scripts build) live in
`conjure_scripting_slow_tests` (`tests/scripting/slow/`, labels `scripting;dotnet;slow`, 900 s timeout),
which the default test presets exclude. `conjure_scripting_api_generated_up_to_date` checks that
`native_api_hash.h`, `managed/Conjure.Managed/Generated/NativeApi.g.cs` and
`docs/generated/native_api_manifest.json` match `native_api.inl`; after editing the table run
`python tools/generate_native_api.py`. The `conjure_managed_sources_match.*` entries check that every
C# project's explicit compile items and the CMake source lists agree.
